# 자산승계 360 — Codex 통합 구현 지시서

작성일: 2026-09-05 · 요청자: 조경호 회계사

이 문서 전체를 이번 작업의 구현·검수 기준으로 사용하라. 문서를 요약하거나 계획만 제시하고 끝내지 말고, 기존 코드를 이어받아 구현·검증·검토용 결과물 제출까지 수행하라. 아래에서 허용한 작업은 단계마다 재승인을 묻지 말고 진행하라. 이 문서는 main 머지, Production 배포, 유료 서비스 결제의 승인이 아니다.

## 1. 이번 작업의 최종 목표

**고객이 쉬운 버튼과 직접 입력으로 답하고, 자신의 가족·자산·목표가 반영된 계산과 실행 시나리오를 확인한 뒤, 가족에게 보여줄 수 있는 A4 7장 보고서를 저장하는 흐름을 완성하라.**

한 번에 맡기는 범위는 기존 Issue #7 계산·시나리오 기반, #6 인터뷰, #5 Report V2를 연결한 통합 구현이다. 공통 타입만 만들거나, 첫 화면만 고치거나, 계산 없는 보고서 틀만 만든 상태에서 작업을 종료하지 마라.

완성할 경로:

```text
랜딩 → 목적 선택 → 버튼·문장 인터뷰 → 추출 후보 확인·수정
→ 확정된 가족·자산 사실 → 기준안·대안 계산 및 적용 범위 판정
→ 개인별 시나리오 비교 → 웹 보고서 → A4 PDF 저장·가족 전달
```

4트랙 모두 인터뷰·사실 확인·시나리오·보고서 경로를 연결한다. 세액은 검증된 지원범위부터 실제 계산한다. 지원범위 밖 계산, 세법 승인, 외부 서비스 연결을 가짜로 채워 완성했다고 주장하지 않는다. 구현 가능한 부분을 모두 끝낸 뒤 남은 장애만 근거와 함께 한 번에 보고한다.

## 2. 확정된 제품 방향

- 제품명은 **자산승계 360**, 고객 관점의 공개 웹·클라우드 서비스다. 내부 회계사용 로컬 전용 프로그램으로 방향을 바꾸지 않는다.
- 최상위 트랙은 `inheritance` 상속, `gift` 증여, `business_succession` 가업상속·가업승계, `capital_gains` 양도다.
- 보험·부담부증여·가족법인·혼합안은 트랙 아래의 검토 수단이다. 가족법인 설립과 가업 관련 특례 충족을 같은 것으로 취급하지 않는다.
- 보고서 자체의 가치가 상담 유도보다 우선이다. 회원가입·전화번호·이메일 제출을 진단과 보고서 열람의 선행 조건으로 만들지 않는다.
- 예상 자산가액, 기준안·대안 예상세액, 예상 절세액, 비용 반영 효과, 구체적 실행 시나리오가 핵심 제품 요구다. 숫자를 전부 숨기는 것은 최종 해법이 아니다.
- **고객 서비스용 AI API 연결은 마지막 별도 단계다. 이번에는 외부 AI API 호출·유료 가입 없이 결정적 규칙, 계산, 인터뷰, 보고서를 연결한다.** 개발용 Codex를 사이트 고객의 실행 엔진으로 사용하지 않는다.
- 한국어를 기본으로 하고, 전문가 용어는 필요한 위치에서 쉽게 설명한다.
- 기존 PR #4 머지는 보고서의 제품 합격을 뜻하지 않는다. 이전 보고서는 사용자에게 불합격 평가를 받았다. 과거 CI 통과·승인 라벨·디자인 점수를 새 완료 근거로 재사용하지 않는다.

## 6. #7 — 모든 화면이 공유하는 사실·계산 계약

```text
ConversationMessage → FactCandidate → ConfirmedFact → ClientFacts
→ CalculationContext → Baseline / Scenario → CalculationResult
→ ComparisonResult → ReportViewModel
```

### 사실과 상태

- 사실은 값, 단위, 당사자/소유자 ID, 출처, 확인상태, 유효 기준일을 추적한다. 보고서 작성자와 재산 소유자를 구분한다.
- 사용자 직접 입력, 사용자 승인 가정, 법령 규칙, 계산 결과, 데모 데이터를 별도로 구분한다.
- 미상 `unknown`, 해당 없음 `not_applicable`, 미계산 `not_calculated`, 검토 필요 `needs_review`, 계산됨 `computed`를 상태 필드로 구분한다. 서로 다른 개념을 한 숫자나 단일 플래그에 압축하지 않는다.
- ‘채무 없음’은 확인된 0원이고 ‘채무를 모름’은 미상이다. 부분 합계는 ‘확인된 자산 합계’처럼 표시하고 총액으로 둔갑시키지 않는다.
- 금액은 원 단위 정수 또는 명시적 정밀도의 Decimal로 처리한다. 안전한 정수 범위를 넘는 입력은 정밀도를 보장하거나 명확히 거절한다. 부동소수점 오차·단위 혼동을 막는다.
- 금액 구간은 구간 그대로 보존한다. 중간값을 확정 입력으로 만들지 않는다. 숫자를 계산할 수 없는 문장은 원문을 보존하고 재확인한다.
- 가족관계·자산·소유지분·기준일·채무·과거증여·보험계약·사업지분·후계자·생활자금·목표·기간·비용·재원을 필요한 범위에서 구조화한다. 취득가액과 현재가액을 구분한다.
- 자산 가치가 전체 자산 기준인지 해당 소유지분 기준인지 저장해 지분을 중복 곱하지 않는다. 보험의 현재 해지/환급가치와 미래 보험금도 중복 합산하지 않는다.

### 버전과 수정

- 입력 스냅샷 ID/버전, 스키마 버전, 규칙 버전, 기준일을 계산·비교·보고서에 연결한다.
- 이전 답변 수정 시 영향받는 후속 사실·계산·시나리오를 무효화하고 재확인/재계산한다. 새 입력에 예전 절세액이 남지 않게 한다.
- 비동기 처리 순서가 뒤집혀 이전 결과가 최신 결과를 덮어쓰지 않게 한다. 웹과 PDF는 동일한 확정 스냅샷의 `ReportViewModel`을 사용한다.
- 새 진단과 기존 진단을 구분한다. 같은 기기에서 다른 가족의 데이터가 섞이지 않게 한다. 기존 프로토타입 저장값이 호환되지 않으면 조용히 삭제하거나 엉뚱하게 변환하지 말고 복구 가능한 안내를 제공한다.

## 7. #7 — 실제 계산과 시나리오 엔진

### 세법 규칙을 검증하고 연결하라

1. 접근 가능한 기존 규칙, 근거 자료, 검토 상태, 계산 코드, 골든케이스부터 조사한다. `SPECIFIED`나 `SME_REVIEW_REQUIRED`는 자동으로 승인 완료가 아니다.
2. 적용 기준일·시행일·납세자/거주자 범위·자산 유형·공제·과거이전·포함 세목을 공식 법령·국세청 등 1차 자료로 확인한다. 세법 MCP 조회 성공 자체는 계산 규칙 승인이나 정확성 증명이 아니다.
3. 기존 승인 범위 내 규칙은 근거와 적용범위를 확인해 재사용한다. 새로운 규칙은 근거·계산 단계·독립된 기대값으로 검증하되 전문가 검토가 필요한 요건을 임의 승인하지 않는다.
4. 가능한 가장 좁은 실제 세액 계산부터 연결하고, 같은 방식으로 검증 가능한 범위를 확대한다. 조사 없이 ‘엔진 없음’으로 끝내지 않는다. 새 구현만으로 전문가 승인 라벨을 만들어 내지 않는다.
5. 각 트랙·지원 케이스별로 입력요건, 포함/제외 세목, 적용 날짜, 규칙 출처, 검토 상태, 테스트 근거를 지원범위 표에 남긴다. 단순 자산 합산을 세액 엔진 완료라고 부르지 않는다.
6. 유효한 근거/규칙/필수 입력이 부족하면 해당 계산만 사유와 다음 확인사항을 반환한다. UI·보고서·다른 지원 계산은 계속 완성한다. 지원 세액 계산이 전혀 없으면 통합 기능의 수치 요구는 미달로 판정한다.

이 지시서는 세율·공제액·특례 요건을 확정하지 않는다. ‘상속재산 10억 이하면 무조건 0원’ 같은 문구를 보편 계산 규칙으로 넣지 않는다. 미래 시행이 미확정인 법안을 현행 규칙으로 쓰지 않는다.

### 비교의 수학과 표시

```text
예상 절세액 = 기준안의 계산범위 내 총예상세액 − 대안의 같은 범위 총예상세액
절세율 = 예상 절세액 / 기준안 총예상세액
총부담 = 계산범위 내 세금 + 해당 비교기간의 실행비용
비용 반영 효과 = 기준안 총부담 − 대안 총부담
```

- 기준안 세액이 0이면 절세율을 산출하지 않는다. 음수 절세액은 ‘추가 세부담’으로 표시한다.
- 미계산 세목이나 비용을 0으로 채워 총부담·절세액을 확정하지 않는다. 일부만 비교 가능하면 공통으로 계산된 범위의 비교임을 명시한다. 실행비용 미상일 때 비용 반영 효과를 확정하지 않는다.
- 동일한 출발 사실·비교기간·평가기준·법령 적용정책·세목 범위를 사용한다. 상속과 양도는 목적에 맞는 기준안을 정의한다. 시나리오 실행에 따른 잔여재산·보유자·발생시점 차이는 정상적인 결과로 반영한다.
- 현재 입력 자산가액과 미래 예상가액을 구분한다. 미래 가액은 사용자가 승인한 기간·자산별 상승률·가정 출처가 있을 때만 계산하며, 없으면 현재가액 기준이라고 표시한다.
- 미래 명목합계와 현재가치를 섞지 않는다. 현재가치 비교를 지원할 때만 할인율과 기준시점을 명시한다. 범위 추정은 같은 전제끼리 비교하며 서로 다른 시나리오의 유리한 끝값을 임의 조합하지 않는다.
- 보험료는 세금이 아니다. 납입 현금흐름, 보험금, 지급시기, 현재 가치, 세무처리를 구분한다. 보험을 넣었다는 이유로 절세액을 부여하지 않는다.
- 작은 양수 금액을 0원으로 표시하지 말고, 음의 순자산을 임의로 0원에 고정하지 않는다. 비용 반영 효과를 가족 전체 재산 증가액으로 과장하지 않는다.

### 시나리오는 구체적인 실행 경로다

36개 시나리오는 AI가 내부적으로 검토하는 후보 라이브러리다. 사용자 화면이나 PDF에는 36개 전체 목록, 전체 매트릭스, 제외된 시나리오 목록을 노출하지 않는다.

사용자에게 보여줄 결과는 현 상태 그대로 상속하는 기준안 1개, 사용자에게 가장 적합한 추천 시나리오 최대 3개, 필요한 경우 추가 검토안 최대 2개, 보험·연부연납 등 납세재원 보완안 1개로 제한한다. 화면에는 `36개 시나리오 내부 분석 완료`라는 사실만 간단히 표시하고 실제 결과에는 추천된 시나리오만 보여준다.

각 시나리오는 다음을 가진다.

- 후보로 제시된 입력 사실과 이유, 적용 가능/조건부/제외 상태 및 이유.
- 실행 날짜/기간, 당사자, 이전 자산·지분·채무, 세목, 실행비용, 현금유출입 이벤트.
- 검증된 예상세액·절세액·비용 반영 효과, 당장 필요한 현금과 확인된 조달 재원.
- 부모 잔여재산·생활자금, 통제권/경영권, 자녀별 배분, 되돌리기 어려운 결정.
- 실행 전 확인할 사실·요건·자료와 의사결정의 선후관계.

현금 부족은 재원 검토의 이유이지 보험 가입의 자동 결론이 아니다. 채무 보유는 부담부증여 검토의 이유이지 유리함의 확정이 아니다. 비상장 지분은 가업 질문을 여는 조건이지 특례 적용 승인이 아니다.

적격성·목표·실행가능성을 먼저 보고 검증된 세액 효과를 비교한다. 비교가 불완전하면 절세 순위나 ‘최적안’을 만들지 않는다. 근거 없는 82점 같은 점수와 고정 추천 순위를 없앤다. 사실상 유효한 후보가 한 개뿐이면 이유를 설명하고 후보 수를 억지로 채우지 않는다.

## 8. #6 — 큰 버튼과 직접 입력이 함께 있는 인터뷰

첫 질문: **“어떤 준비를 고민하고 계신가요?”**

선택지: 상속 / 증여 / 가업·회사 승계 / 양도 / 여러 방법 비교 / 아직 잘 모르겠어요.

‘여러 방법 비교’와 ‘아직 잘 모르겠어요’는 탐색 흐름이지 새 최상위 세금 트랙이 아니다. 필요한 후속 질문으로 관련 트랙을 좁힌다.

### 대화 흐름

- 현재 질문 하나를 강조하고 과거 답변은 위에 쌓는다. 큰 선택 버튼과 문장 입력창을 동시에 제공한다.
- 첫 화면을 긴 설명·카드 목록으로 채우지 않는다. 모바일에서 현재 질문과 첫 답변 버튼이 보이게 한다.
- 질문마다 ‘왜 물어보나요?’ 설명과 ‘모르겠어요/나중에 확인’을 제공한다. 도움말을 본 뒤 원래 질문으로 돌아온다.
- 필수 최소 질문부터 묻고 관련 답변에 따라 확장한다. 네 트랙의 모든 질문을 모든 고객에게 강요하지 않는다.
- 공통으로 작성자/재산 소유자, 가족관계, 자산·채무, 과거이전, 목표·기간·생활자금 등을 필요한 시점에 확인한다. 가족관계로 나이·성년·거주자 여부를 추론하지 않는다.
- 상속은 피상속 예정자/상속 개시 여부·시점, 가족·귀속·이전 이력을, 증여는 주는 사람/받는 사람·대상·시점·이전 이력을, 양도는 소유자·자산·취득·처분 관련 사실을, 가업은 지분·사업·경영 참여·후계자·승계 목표를 지원 규칙에 필요한 범위로 묻는다.
- 복수선택은 ‘선택 완료’로 제출한다. 답변 수정·뒤로가기·새로고침·재개·새 진단 시작이 일관되게 동작하게 한다.

### 직접 문장 입력

반드시 `원문 → 추출 후보 → 고객 확인 → 확정 사실` 순서를 지킨다. 명확한 버튼 입력은 직접 확정할 수 있으나 자유문장 후보를 확인 없이 계산에 사용하지 않는다.

최소 지원 예와 금지 추론:

| 문장 | 처리 |
|---|---|
| 현금 5천만원 있어요 | 현금 50,000,000원 후보를 만들고 소유자를 확인 |
| 자녀 둘 있어요 | 자녀 수 2명 후보만 생성; 성년 여부·성별은 만들지 않음 |
| 아버지 재산이에요 | 재산 소유자와 작성자의 관계를 확인; 작성자 재산으로 자동 저장 금지 |
| 아파트 두 채 있어요 | 자산 종류·개수 후보; 시가나 소유지분은 추가 질문 |
| 대출 없는 것 같아요 | 불확실성을 보존하고 확인; 확정 채무 0원 처리 금지 |
| 아니요, 아까 5억이 아니라 3억이에요 | 현재 대상이 명확하면 정정 후보를 제시, 모호하면 어느 자산인지 질문 |

현재 질문에 맞는 수량·금액·관계·부정/미상 표현을 제한된 결정적 해석기로 처리한다. 여러 뜻이 가능한 문장은 추가 확인하고, 지원하지 못하는 문장은 고객 메모/확인 질문으로 남긴다. 입력을 이해한 척 임의 답을 만들지 않는다.

‘조회계사’ 캐릭터를 쓰더라도 자동 인터뷰임을 명확히 한다. 회계사 본인이 실시간 답하는 듯한 접속 상태나 가짜 AI 생성 문구를 넣지 않는다.

### 사용성·저장

- 모바일 본문 약 18px 이상, 주요 버튼 높이 약 56px 이상, 충분한 대비·포커스·라벨을 확보한다.
- 한글 IME 조합 중 Enter는 전송하지 않고 조합 완료 후 전송한다. 빠른 연속 클릭·Enter로 답변이 중복 저장되지 않게 한다.
- 모바일 가상 키보드가 현재 입력창·전송 버튼을 가리지 않게 한다. 키보드 접근과 오류 안내도 확인한다.
- 대화 이력·현재 질문·확정 사실·미확정 후보·초안을 함께 저장하고 재개한다. 기존 저장 방식의 실제 보존 범위에 맞춰 안내한다. 같은 탭 새로고침 재개와 브라우저 종료 후 재개를 혼동하지 않는다.
- 저장 정책은 현재 환경과 기존 설계에 맞춰 구현한다. 지속 보관을 새로 도입하면 고객의 저장 선택·삭제 수단·보존 범위를 제공하고 미검증 보안 문구를 쓰지 않는다.
- 결과 생성 전 입력 요약에서 고객이 확인·수정할 수 있게 한다. 필수 정보 부족이면 정확히 필요한 질문으로 돌아가며 전부 다시 입력시키지 않는다.

## 9. #5 — 가족이 보관할 가치가 있는 Report V2

웹 보고서와 A4 세로 PDF는 동일 데이터로 만들되 레이아웃은 각각 설계한다. 웹 화면을 길게 찍어 인쇄하는 방식으로 끝내지 않는다. **기본 보고서는 정확히 7장**이며 각 장의 역할은 다음과 같다.

| 장 | 고객의 질문 | 필수 내용 |
|---|---|---|
| 1 | 지금 무엇이 중요하고 얼마가 예상되나? | 표지+요약, 확인된 현재 자산가액/조건부 미래가액, 기준안·대안세액, 절세액·비용 반영 효과, 주요 발견과 우선 검토 방향 |
| 2 | 우리 가족과 재산은 어떻게 연결되나? | 가족·자산 지도, 실제 소유자·지분, 자산 비중, 확인된 채무·과거이전, 중요한 미상정보 |
| 3 | 현 상태로 두면 얼마와 어떤 재원이 필요한가? | 현 상태 기준 상속세와 납세재원, 확인 과세표준 여부, 현재가액과 과세표준의 구분 |
| 4 | 기준안과 추천안은 무엇이 다른가? | 기준안과 AI 추천 3개만 세금·현금·기간·위험 기준으로 비교 |
| 5 | 추천안 1·2는 어떻게 실행되나? | 추천안 1·2의 당사자, 대상자산, 필요현금, 선행 확인사항 |
| 6 | 추천안 3과 재원 보완은 무엇인가? | 추천안 3, 보험·연부연납 등 납세재원 보완안, 필요한 경우 추가 검토안 최대 2개 |
| 7 | 실행 전 무엇을 합의하고 확인하나? | 실행 로드맵, 주의사항, 공식 근거, 준비자료·미확인사항, 재검토 시점 |

### 내용의 합격 기준

- 1장은 고객 결론이 중심이다. 내부 ID·오류 코드·상담 CTA가 요약보다 크게 나오지 않는다.
- 고객마다 가족·자산·목표·기간에 따라 발견사항·후보·타임라인·준비자료가 달라져야 한다. 이름과 총자산만 바뀌는 고정 문서는 불합격이다.
- 금액에는 산정 범위·기준일·조건을 인접하게 표시한다. 일부 세목만 계산했으면 그 세목의 예상액이라고 쓴다.
- 정보가 부족해도 확인된 사실로 판단 가능한 내용, 추가 정보가 판단에 미치는 영향, 먼저 확보할 자료를 구체적으로 제시한다.
- 미계산 이유는 핵심 공통 사유로 묶고 필요한 위치에서 참조한다. ‘추가정보 필요’ 수십 칸, `--`만 있는 비교표, ‘향후 계산’ 카드로 지면을 채우지 않는다.
- 고객이 입력하지 않은 자산·채무·성년 여부·시가·상승률·세액을 만들지 않는다. `mockData.ts`는 명시적 데모 모드/테스트에만 쓰고 실사용 보고서에 fallback하지 않는다.
- 예시 보고서를 제공할 때는 명확히 ‘가상 사례’로 표시하고, 실제 인터뷰 스냅샷과 저장 공간·생성 경로를 분리한다.
- 검토 근거를 요약하되 회계사가 직접 검토·승인했다는 서명/문구를 자동 삽입하지 않는다. 법적 효과나 절세를 보장하지 않는다.

### 디자인·인쇄의 합격 기준

- 네이비·아이보리·절제된 골드의 패밀리오피스 톤으로 통일한다. 과도한 그라데이션·장식·아이콘·홍보 문구를 줄인다.
- A4 본문은 10.5pt 이상을 목표로 한다. 잘림을 숨기려고 글자를 계속 줄이지 않는다. 표가 넓으면 주제를 나누어 비교한다.
- 작성일, 평가/계산 기준일, 보고서 버전, 보고서 ID, 페이지 번호를 일관되게 둔다. ID는 조용한 메타정보로 배치한다.
- 한글 폰트·숫자·기호가 PDF에서 정상 출력되어야 하며 텍스트 선택/검색이 가능해야 한다. 차트는 원본 수치와 일치해야 한다.
- 기본 7장 내에서 중요 정보를 빠뜨리지 않게 요약·레이아웃을 조정한다. 항목이 많으면 합계가 대사되는 그룹 요약과 웹 상세로 처리하고 요약 사실을 표시한다. 조용한 누락·잘림·강제 숨김은 금지한다.
- 행·카드 분리, 하단 넘침, 제목만 남는 페이지, 빈 페이지를 막는다. 의도적 여백은 허용하되 장수를 맞추기 위한 빈 내용은 금지한다.
- 이전 불합격 PDF·캡처는 문제 확인용이며 디자인 합격 견본이 아니다. 새 PDF는 실제로 7장 각각 렌더링하여 읽고 수정한다.

## 10. 결과·공유·상담의 실제 동작 범위

- 이번 가족 공유 완료 기준은 **다른 기기에서도 내용을 볼 수 있는 PDF 파일을 고객이 저장하고 전달할 수 있는 것**이다. PDF에는 수신자가 이해할 기준일·전제·계산상태가 포함되어야 한다.
- `sessionStorage` 안에만 있는 진단 ID URL을 공유 기능으로 표시하지 않는다. 보고서 없는 URL에 ‘링크 복사 완료’나 ‘가족 공유 완료’를 띄우지 않는다. 데이터가 없거나 유효하지 않으면 명확한 안내를 표시하고 예시 결과로 대체하지 않는다.
- 서버 스냅샷·만료·철회·접근제어를 갖춘 가족 공유 링크는 후속 범위다. 이미 검증된 기존 구현이 있는 경우에만 그 실제 동작을 확인해 유지한다. 이번 완료를 위해 새 클라우드 계정·유료 저장소를 임의 도입하지 않는다.
- 상담은 선택 사항이다. 실제 접수 API와 저장/전달 경로가 확인되지 않으면 ‘접수 완료’라고 표시하지 않는다. 이미 확인된 연락 경로를 사용하거나 기능 상태를 솔직히 안내한다. 연락처를 지어내지 않는다.
- 공개 메뉴에서 전문가 콘솔로 유도하지 않는다. 메뉴 숨김은 인증이 아니다. 공개 Preview에 실데이터·민감 기능을 넣지 말고, 기존 인증이 없으면 전문가 화면은 실제 데이터 없는 프로토타입임을 구분한다.
- 개인 이름·상세주소·연락처·자산정보를 URL 쿼리, 공유 미리보기, analytics, 콘솔, 에러 로그, 외부 AI에 흘리지 않는다. 회귀 테스트·PR·캡처·PDF 증빙에는 가상 데이터를 사용한다.

## 11. 반드시 통과시킬 검증

프로젝트에 실제 존재하는 설치·검증 명령과 CI의 서버 실행 절차를 먼저 확인한다. 인수인계의 예시는 `npm ci`, `npm run lint`, `npm run typecheck`, `npm run build`, `node scripts/ui-audit.mjs`, `node scripts/pdf-audit.mjs`, `node scripts/pr2-smoke.mjs`다. 명령이 없거나 환경이 다르면 실제 설정에 맞게 연결한다. 기존 미커밋 폴더를 초기화하지 말고 필요하면 격리된 작업 경로에서 설치한다.

### A. 금액·사실 회귀검증

| 입력/상황 | 기대 동작 |
|---|---|
| `5000만원`, `5천만원`, `0.5억` | 모두 50,000,000원; 금액 파서의 직접 기대값으로 검증 |
| `3억 5천만원` | 350,000,000원 |
| 단위 없는 `5000` | 화면에서 원 단위가 명시된 입력이면 그 단위 적용; 자유문장 등 단위가 불분명하면 재확인 |
| 채무 없음 / 채무 모름 / 채무 미응답 | 확인된 0 / 미상 / 미응답을 구분; 미상값을 0으로 합산하지 않음 |
| 자산 50억 입력 | 다른 예시 자산 55억이나 입력하지 않은 채무 8억·3억·11억이 보고서에 나오지 않음 |
| 자녀 둘 / 아버지 재산 / 아파트 두 채 | 인원·관계·개수만 반영; 성년·소유자·금액 추측 없음 |
| 범위 입력 / 음의 순자산 / 작은 양수 | 범위를 보존, 음수를 숨기지 않음, 양수를 0원으로 축약하지 않음 |
| 혼합단위·불가능한 지분·잘못된 날짜·과도한 금액 | 지원 형식이면 정확히 처리; 모호·유효성 오류면 원문을 보존하고 정정 안내 |
| 이전 답변 정정 | 후속 사실 재확인 및 계산·웹·PDF 모두 같은 최신 스냅샷으로 갱신 |

### B. 계산·비교 검증

- 지원 규칙마다 실제 독립 기대값이 있는 골든케이스를 확보한다. 구현 함수를 다시 호출한 값을 기대값으로 삼지 않는다. 공식 사례 또는 재현 가능한 별도 산식을 근거와 함께 남긴다.
- 해당 규칙의 경계값·날짜 경계·누락 입력·미지원 조건·반올림을 검증한다. 상속/증여/양도/가업 특례를 하나의 계산식에 무리하게 공통화하지 않는다.
- 기준안 0원, 절세액 음수, 실행비용 미상, 일부 세목 미계산, 기간/세목 불일치에서 잘못된 절세율·총부담·순위를 내지 않는지 검증한다.
- 자산 이전·매각·현금증여 이벤트가 중복 합산되지 않고 현금·잔여재산 흐름이 연결되는지 검증한다. 보험료와 세금을 분리한다.
- 동일 입력·기준일·규칙 버전이면 동일 결과가 나와야 한다. 입력 스냅샷과 계산 결과의 연결을 추적할 수 있어야 한다.

### C. 인터뷰·보고서 통합검증

- 네 트랙마다 서로 다른 가상 가족 fixture를 만든다. 상속은 가족·복수 자산·채무, 증여는 당사자·과거이전, 가업은 비상장 지분·미확인 특례, 양도는 취득/처분 사실을 포함한다. 세액 지원 여부에 맞는 기대 동작을 명시한다.
- 추가로 미상정보가 많은 사례, 모순 입력, 긴 이름·많은 자산·긴 설명 사례를 사용한다. 모순 입력은 임의 정상화하지 않는다.
- 목적 선택부터 직접 입력, 후보 확인, 수정, 도움말 복귀, 새로고침 재개, 결과, PDF까지 실제 브라우저로 확인한다.
- 최소 데스크톱 1440px와 모바일 390px에서 검증한다. 한글 IME·가상 키보드는 실제로 확인한 환경과 자동화만으로 확인하지 못한 부분을 구분한다.
- 각 트랙의 PDF가 7장이고 입력 사실·숫자·ID가 웹과 일치하는지 확인한다. 각 장을 PNG로 렌더하여 내용·넘침·잘림·한글 폰트를 눈으로 검수한다. 파일 생성 성공만으로 통과시키지 않는다.
- 신규 핵심 테스트가 실제 CI에서 실행되도록 연결한다. 테스트를 삭제/skip하거나 assertion을 약화해 통과시키지 않는다. 도구가 없으면 실행하지 못한 항목을 PASS로 보고하지 않는다.

## 12. PR·Preview와 검토용 증빙

- 작업 브랜치의 변경 범위·보존 상태를 검토한 뒤 커밋한다. 비밀값·실제 고객 데이터·무관한 로컬 파일이 포함되지 않게 한다.
- 기존 #5·#6·#7을 참조하는 통합 PR을 작성한다. 각 이슈별 실제 충족/미충족 범위를 명시하며, 남은 요구가 있는 이슈를 자동 종료하는 문구를 쓰지 않는다. 준비 중이면 draft를 유지하고 임의 merge하지 않는다.
- 기존 Vercel 프로젝트의 실제 팀/프로젝트 ID, 루트, 환경, 브랜치별 배포 정책을 확인한다. 이름을 추측해 새 프로젝트를 만들지 않는다.
- **최종 코드 커밋을 포함하는 정확한 PR HEAD의 Preview**를 확인한다. URL, deployment ID, target=Preview, commit SHA, 접근 상태를 남긴다. 브랜치명이나 과거 배포 링크만으로 동일성을 주장하지 않는다.
- Preview가 SSO로 보호되면 검토 링크의 보호 상태를 명시한다. ‘비로그인 공개 서비스 완료’라고 하지 않고 보호 해제·인증 우회를 하지 않는다.
- Preview가 막혀도 로컬 구현·테스트·PDF·PR 등 가능한 작업을 먼저 완료한다. 접근권한이 필요한 한 부분만 마지막에 분리한다.
- 증빙에는 최종 SHA, 명령·종료결과·실행 환경, 네 트랙 데스크톱/모바일 캡처, PDF 4개와 장별 PNG, 지원범위 표, 알려진 결함을 포함한다. 테스트 산출물은 프로젝트의 기존 방식 또는 접근 가능한 검토 첨부로 제공하고 대형 파일을 무조건 소스 Git에 쌓지 않는다.
- 증빙 문서에 자기 자신의 최종 커밋 SHA를 넣느라 커밋을 반복하지 않는다. SHA는 PR 본문·CI artifact 등 확정 이후 기록 가능한 위치에서 코드와 대응시킨다. 코드 변경 후에는 영향을 받는 검증·Preview를 갱신한다.

## 13. 완료 판정 — 코드 통과와 제품 합격을 구분

아래 각 항목을 `PASS / FAIL / NOT_RUN / BLOCKED`로 판정하고 증거를 연결한다.

| 게이트 | 충족 조건 |
|---|---|
| 기존 작업 보존 | 무관한 삭제/덮어쓰기 없이 기존 변경·비밀값·문서 보존 |
| 네 트랙 연결 | 네 목적별 질문·확인·수정·재개·결과·보고서 경로 실제 동작 |
| 사실 정확성 | 원문/가정/미상/0 구분, 단위·소유자·지분·스냅샷 일치 |
| 실제 수치 계산 | 검증된 지원 세액을 엔진으로 계산하고 지원범위·독립 기대값 제시 |
| 의미 있는 대안 | 사실·목표에 연결된 후보와 실행 이벤트, 가능한 범위의 공정한 금액 비교 |
| 보고서 내용 | 고객별 결론·근거·전제·준비사항이 연결되고 고정 예시·빈 칸 반복 없음 |
| 7장 PDF | 네 트랙의 실제 7장 PDF와 장별 시각 검수, 잘림/한글 오류 없음 |
| 기술 검증 | 실제 설정의 lint/typecheck/build 및 핵심 테스트·CI 결과 제시 |
| Preview 대응 | 최종 코드 SHA와 Preview 대응 및 접근 상태 확인 |
| 정직한 기능 표시 | AI·상담 접수·가족 URL 공유·전문가 검토·공개 여부를 실제 상태와 일치시킴 |

판정 규칙:

- `READY_FOR_REVIEW`: 이번 범위의 필수 게이트를 증거로 충족하여 사용자가 검토할 수 있음. **사용자의 제품 승인·머지 승인·상용 출시 승인을 뜻하지 않는다.**
- `BLOCKED_WITH_REASONS`: 필수 계산·검증·접근 등 충족하지 못한 게이트가 있음. 구현된 부분은 그대로 제출하고 막힌 게이트, 수행한 시도, 필요한 입력/승인만 정확히 적는다.
- 지원범위 밖 복잡 사례는 지원표에 명확히 구분한다. 그 존재만으로 검증된 좁은 지원범위의 구현을 무효화하지 않되, 네 트랙 모든 세액과 특례가 완성되었다고 표현하지 않는다.
- 기준안/대안의 유효한 수치 비교를 하나도 증명하지 못하면 숫자 요구를 충족한 것으로 판정하지 않는다. 전체 숫자 마스킹, 인터페이스만 구현, PDF 장수만 충족한 상태는 합격이 아니다.
- 서버 가족 공유와 고객 AI API는 이번 범위 밖 후속 과제로 별도 표시한다. 이번 작업의 필수 미충족과 후속 기능을 섞지 않는다.

## 14. 작업 방식과 최종 보고

색상·문구·컴포넌트·타입 배치 같은 되돌릴 수 있는 구현 선택은 기존 맥락과 이 기준으로 스스로 결정하라. ‘계속할까요?’, ‘다음 단계도 할까요?’를 반복하지 말고 구현과 결함 수정을 이어가라. 진행 상황은 확인한 사실과 다음 해결 대상을 짧게 알려라.

권한이 없거나 공식 근거/전문가 검토가 반드시 필요한 경우에는 그것을 우회하지 않는다. 해당 부분을 분리하고 나머지 허용 범위의 구현·검증·검토 자료를 끝낸 후 꼭 필요한 질문만 한 번에 모아라. 다른 AI에게 전달했다거나 GitHub 댓글을 썼다는 사실을 실제 실행·완료로 보고하지 마라.

최종 응답은 아래 형식으로 작성하라. 긴 작업일지 대신 실제 결과와 확인 가능한 증거를 제시한다.

```text
최종 판정: READY_FOR_REVIEW / BLOCKED_WITH_REASONS
검토한 main SHA / 작업 브랜치 / 최종 PR HEAD SHA:
PR 및 연결 이슈 #5·#6·#7:
고객이 직접 사용할 수 있게 된 흐름:
실제 계산 가능한 세목·조건·기준일 / 지원하지 않는 범위:
전문가 검토가 필요한 규칙과 정확한 검토 질문:
웹·PDF에 연결된 기준안·대안 비교 사례:
실행한 검증 명령·결과·환경 / 실행하지 못한 검증:
4트랙 PDF 및 각 장 PNG·데스크톱/모바일 캡처 위치:
Preview URL / deployment ID / target / commit / 접근 상태:
기존 변경 보존 확인 / 삭제·과금·main push·merge·Production 여부:
필수 게이트 미충족 / 후속 범위 / 남은 제품상 약점:
사용자 확인이 꼭 필요한 사항(없으면 없음):
```

**지금 실제 저장소와 작업 상태를 확인하고 구현을 시작하라. 문서 작성·작업 계획·타입 정의·부분 화면만으로 이번 작업을 종료하지 마라.**

작성 근거: 사용자가 제공한 `START_IN_COWORK (1).txt` 및 `ASSET_SUCCESSION_360_COWORK_HANDOFF (1).md(1).crdownload`. 본 지시서 작성은 첨부 자료의 제품 결정과 작업 경계를 통합한 것이며, 원격 저장소·로컬 코드·법령·배포를 새로 검증한 결과 보고서가 아니다. 실행 시 최신 증거로 상태를 확인한다.
