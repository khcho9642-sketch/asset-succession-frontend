# 자료실 분류 스키마

이 파일은 **분류 설계안**이며 기존 저장소 데이터의 마이그레이션 결과가 아니다. 기한과 법정 요건의 숫자, 계약·유언의 법률 문안은 포함하지 않는다.

- `resource.schema.json`: 공개 자료·탐색 묶음 레코드. 원본 확보 상태와 분류 검토 상태를 분리한다.
- `deadline-case.schema.json`: 비공개 사건별 기한 작업 레코드. 고객의 사건 발생일·계산된 기한은 여기에만 저장한다.

## 탐색 단계

| ID | 명칭 |
|---|---|
| S1 | 현황 정리 |
| S2 | 방법·재원 설계 |
| S3 | 의사·계약 확정 |
| S4 | 권리 이전·수령 |
| S5 | 신고·납부 |
| S6 | 유지·사후관리 |
| S7 | 정정·분쟁 대응 |

순서는 탐색 우선순위이며 법정 절차 순서나 모든 사용자에게 요구되는 진행 단계가 아니다. 단계별 집계에는 `primary_stage_id`를, 실제 검색에는 중복 소속이 가능한 `stage_ids`를 쓴다. 분류 근거가 없으면 `primary_stage_id: null`, `stage_ids: []` 및 검토 메모를 저장한다. `미분류`는 관리 상태이며 탐색 단계를 추가하지 않는다.

## 패싯과 미확인 값

`purposes`, `timing`, `assets`는 다중 선택이다. 선택 목록이 비어 있으면 **확인 필요**이며 전체 해당이나 해당 없음으로 해석하지 않는다. `other`는 실제 기타 자산·역할이고 미확인의 대체값이 아니다. `authority: unknown`도 법정 서식이 아니라는 판정이 아니다.

`facets.origin: unknown`은 제공 주체 미확인이다. 원본·출처가 미확보인 자료에 제공 주체를 추정하여 넣지 않는다.

`facets.timing`의 `before_death`는 생전의 준비와 실행을 모두 포함한다. 일반 조회 자료를 사후 전용으로 단정하지 않는다.

`facets.origin`은 제공 주체, `facets.authority`는 규범적 성격, `facets.delivery`는 제공 방식이다. `official_link`는 해당 자료 제공기관의 공식 페이지 연결로, 민간 금융회사·보험회사 공식 페이지에도 사용할 수 있다. 국세청 등 공공기관이라는 뜻으로 읽지 않는다. 연결 확인과 원본 파일 확보는 다른 상태다.

`source_verification.status`는 출처·원본 확인, `classification.status`는 분류 판단 검토다. 두 값을 하나의 완료 체크로 합치지 않는다. `hosted`이면 `access.hosted_file_ids`에 실제 불변 원본 파일 ID가 있어야 한다. `original_files`는 확보한 파일만 기록하며 링크 자료에 가상의 해시나 파일명을 만들지 않는다.

목적별 적용 조건은 `applicability[]`에서 목적·당사자 역할·조건 설명·근거를 함께 저장한다. 공통 서식이라는 추정만으로 모든 목적 태그를 붙이지 않는다. 이 조건 설명은 자동 법률 판단식이 아니다.

## 준비 가능한 시기와 기회의 창

공개 자료의 `planning_windows[]`는 **준비 가능한 조건과 그 가능성이 달라질 계기**를 담는다. `deadline`은 제출·이행 기한의 규칙 참조이고, `planning_windows`는 정성적 준비 안내다. 어느 한쪽에서 다른 쪽의 기한이나 자격을 자동 추론하지 않는다.

| 필드 | 의미 |
|---|---|
| `window_id` | 자료 안에서 유일하고 유지되는 준비 시기 ID |
| `type` | `capacity` 의사결정 능력 관련 / `event` 사건 관련 / `lead_time` 준비 선행성 / `eligibility` 적용 자격 관련 / `unknown` 확인 필요 |
| `label` | 준비 시기를 설명하는 정성적 제목 |
| `availability_conditions[]` | 준비 가능 조건 또는 확인할 조건 |
| `closing_events[]` | 준비 가능성이 달라질 수 있는 계기. 날짜나 확정 마감일이 아님 |
| `purposes[]`, `party_roles[]` | 적용 목적과 당사자 역할. 미확인은 빈 배열 |
| `evidence_refs[]`, `verification` | 근거와 검증 상태. 출처 확인과 개별 사건 판단을 구분 |
| `rule_ref` | 필요한 경우 준비 조건 규칙 참조 |
| `display_policy` | 항상 `qualitative_only` |

이 필드는 필수 배열로 두고 아직 검토하지 않은 자료에는 `[]`를 넣는다. 빈 배열은 “기회의 창이 없음”을 뜻하지 않는다. 등록된 항목이 `pending` 또는 `needs_review`이면 미확인 사유를 `verification.note`에 남기고, 화면에서는 확인 필요로 표시한다. 검증 전 문구를 확정적 실행 안내나 긴급 경고로 노출하지 않는다.

`verified`는 원문에 근거한 일반 조건 설명을 검토했다는 뜻이다. 개인의 판단능력·계약능력·자격 또는 특정 세무 효과를 확정했다는 뜻이 아니다. 검증된 항목은 근거·검토자·검토 시점과 적용 목적·역할·조건을 갖춰야 하며, `type: unknown`은 검증 완료로 표시할 수 없다. 근거와 적용 범위가 바뀌면 `needs_review`로 되돌린다.

임의후견의 계약 준비 가능 조건과 효력 발생 조건은 서로 구분해 확인한다. 사전증여의 준비 선행성도 행위 자체의 가능 여부나 일정 세무 효과를 자동 보장하는 마감으로 표현하지 않는다. 두 주제 모두 이번 스키마에서 법률 판단이나 기간을 확정하지 않는다.

고객의 사건 날짜, 남은 기간, D-day, 개인별 창의 개폐 판정은 이 공개 필드에 저장하지 않는다. 자유문장에도 사건 날짜·법정 기간 수치·자동 자격 판단을 넣지 않는지 별도 콘텐츠 검토가 필요하다. 직접 진입은 전체 자료를 표시하고 생전 우선은 추천 순서로 적용하며, `planning_windows`의 존재 여부로 첫 화면 우선순위를 임의 변경하지 않는다.

## 관계를 구분하는 방법

| 관계 | 의미 | 카드 처리 |
|---|---|---|
| `ui_member_of` | 사용자 탐색용 묶음에 속함 | 원본과 절차는 독립 유지 |
| `equivalent_to` | 같은 서식의 실질적 중복으로 검증됨 | 대표 카드만 노출 가능, 원본·출처 이력 유지 |
| `subform_of` | 제공기관 근거로 본서식의 실제 부표·첨부서식임 | 본서식 아래 배치 |
| `example_for` | 해당 서식을 설명하는 작성사례 | 사례 탭이나 관련 자료에 연결 |
| `attachment_of` | 관련 참고자료·안내자료 | 부표라고 표시하지 않고 참고자료로 연결 |

탐색 묶음은 `catalog_role: navigation_group`, `facets.kind: toolkit`으로 작성한다. 기존 원본 자료는 `catalog_role: resource`를 유지한다. 묶음 자체는 기관 서식으로 집계하지 않는다. 같은 주제에 속한다는 이유만으로 `equivalent_to` 또는 `subform_of`를 만들지 않는다.

## JSON Schema 밖에서 검증할 불변 조건

1. ID는 카탈로그 전체에서 유일해야 한다. 모든 파일·관계·출처 개정·규칙·절차 참조는 실제 대상을 가리켜야 한다.
2. `primary_stage_id`가 있으면 `stage_ids`에 포함되어야 한다. `null` 레코드는 단계 합계에서 제외하여 미분류로 별도 집계한다.
3. 서로 다른 패싯은 AND, 한 패싯 내부의 복수 선택은 OR로 검색한다. 단계별 복수 소속 검색 결과는 `resource_id`의 합집합으로 세며 중복 합산하지 않는다.
4. `ui_member_of`, `subform_of`, `example_for`, `attachment_of`에는 자기 참조나 순환이 없어야 한다. `equivalent_to`는 동치 묶음으로 정규화하고 대표 ID는 하나만 둔다. 대표 ID는 대표 자신을 다시 중복 대상으로 가리키지 않는다.
5. `subform_of`와 `equivalent_to`의 카드 강등·대표화는 관계 근거를 검증한 뒤 적용한다. 미검증 후보 관계는 자동으로 숨기지 않는다. `within_parent`는 검증된 부모 연결을 필요로 한다.
6. 탐색 묶음은 하위 자료의 법적 절차를 합치거나 대체하지 않는다. 각 원본의 `procedure_ids`를 보존하고 묶음이 여러 절차를 포함함을 허용한다. 별도 신고·청구·신청을 단일 절차로 취급하지 않는다.
7. 원본 파일은 바이트·파일 ID·해시를 유지한다. 개정본은 새 파일·개정 ID로 추가한다. 카드 통합과 숨김은 원본 삭제가 아니다. 기존 링크는 대표 카드나 묶음 내부의 해당 원본으로 연결한다.
8. `hosted_file_ids`와 모든 `source_revision_ref`는 해당 원본 레코드와 맞아야 한다. 출처 확인 완료를 파일 확보 완료로 변환하지 않는다. 서식 수·실제 확보 파일 수·단독 카드 수·묶음 수는 각각 집계한다.
9. `deadline.rule_bindings`는 행위·절차·목적·당사자 역할별 규칙 **참조**다. 기한의 존재 자체가 미확인이면 `unknown`, 기한 없음도 원문 확인 전에는 `not_applicable_verified`로 확정하지 않는다. 하나의 카드에 여러 독립 기한이 있을 수 있다.
10. D-day는 사건 작업에서 규칙 원문·유효 개정·목적/역할 적용·필요 사건일·기산 및 달력 처리 조건이 검증된 때만 계산한다. 미래 시행·경과조치·정정된 사건일이 영향을 주면 재평가한다. 공개 카탈로그에는 고객 날짜나 사건별 D-day를 쓰지 않는다.
11. D-day는 현재 열려 있는 개별 행위의 기한이다. 카드나 묶음에 포함된 다른 작업까지 완료되었다고 표시하지 않는다. 묶음에서 가장 가까운 기한을 요약할 경우 해당 행위명을 함께 보여준다. `completed`는 해당 작업만의 완료이고 기한 경과는 자동 완료가 아니다.
12. `deadline_evaluation.state: verified`일 때 모든 사건 사실과 연결 규칙의 검증 근거가 실제로 존재해야 한다. 스키마의 boolean만으로 법률 정확성이 증명되지는 않는다. 날짜·URI는 검증 라이브러리의 format 검사도 활성화한다.
13. `planning_windows[].window_id`는 한 자료 안에서 중복되지 않아야 하며, 근거·규칙 참조는 실제 대상을 가리켜야 한다. `evidence_refs`와 검증 기록의 근거는 같은 조건 설명을 뒷받침해야 한다. JSON Schema는 자유문장의 법률 정확성이나 수치·사건 날짜의 혼입을 판정하지 못하므로 콘텐츠 검토로 확인한다. 기회의 창을 법정 기한이나 개인의 확정 자격으로 변환하지 않는다.

## 생전 설계 콘텐츠

기관 서식이 없으면 `worksheet`·`guide`·`toolkit`·`service_link`로 표현한다. 자체 작성 콘텐츠는 `origin: editorial`, `authority: editorial`로 명시하고 기관 서식 수와 별도 집계한다. 민간 상품은 실제 제공기관 페이지와 상품 정보를 확인한 뒤 연결한다. 양식의 유무나 법률 요건을 검증하지 않은 상태에서 제출 가능한 법정 서식이라고 안내하지 않는다.

`planning_windows[].impact`는 선택 가능성 변화(`option_availability`)와 기대 효과 변화(`expected_effect`)를 구분한다. 확인되지 않았으면 `unknown`으로 남긴다. 사전증여를 일률적인 실행 불가 마감으로 바꾸지 않는다.
